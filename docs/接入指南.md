## 请求与回调边界

`WechatListener.onSubmitted(requestId, status)` 表示发送受理；`REQUESTED` 不表示最终分享、登录或转账成功。`onReceipt(WechatReceipt)` 保留 SDK `errorCode`、授权 Code 或页面 `result`。宿主不得记录 Code、state、package、原始回跳 URL 或 SDK 原始错误文本。

`cancel(requestId)` 只结束本地等待，不能关闭微信页面。只有对应 pending 成功清除（Android 尚未执行的入队请求成功终止）后才通知 `CANCELLED`；未知或已完成 ID 不产生取消通知。Kuikly 异步取消若持久清除失败，不把它转换成原请求的 `FAILED` 或 `CANCELLED`：可信内存 pending 和 owner 保留，原提交受理/迟回执仍属于该请求，调用方可重试取消。Preferences flush 异常不能证明磁盘一定未写，宿主仍须遵守 store 的同步原子契约；失败恢复缓存仅避免同进程误认为 journal 已成功清除。

此取消确认协议已包含于 Maven/HAR 0.1.4 prerelease；Maven 0.1.5 沿用此协议，原生 HAR 保持 0.1.4；现有远程 0.1.3 HAR 不返回取消 ack，不能与新 Module 混用。Android/Swift 取消 API 未改变。历史版本在 OHOS 图像资源释放失败时保留可信 pending；本源码的图片仅受理合同中，资源释放失败不改变已受理结果，也不重建业务等待。

- Android/OHOS 每个进程级实例在准备与发送时保留单笔占用；普通图片受理后释放，授权、网页及转账继续保留可信回执等待。内部随机 `transaction` 与请求类型精确匹配，OAuth 成功、取消和失败均严格匹配安全随机 state。重复和已取消请求的迟到回执被忽略。
- iOS 只有 OAuth 带 state；分享/转账 SDK 2.0.7 的 `BaseResp` 没有 `transaction`，`requestId == nil` 保持不变。仍可关联的网页从准备到回执只允许一笔；合法网页回执返回 `candidateRequestId`（Swift `candidateRequestID`）和 `attribution=SINGLE_PENDING`，只是当前唯一等待任务的本地候选，不能宣称 SDK 准确关联。Android/OHOS transaction 校验及 iOS OAuth state 校验返回 `VERIFIED`；转账没有候选，返回 `UNATTRIBUTED`。宿主可按候选推进普通分享任务流程；严格抗重复、跨进程迟回执或资金动作必须另行核验，不能将候选升级为 VERIFIED。
- 图片仅等待 SDK 真实受理，随后释放占用。iOS 网页在仍可关联候选时保留单笔等待；图片受理或已收到图片回执、或已发送网页被取消后，`canCorrelateShareReceipt=false`，后续网页也只等受理，分享回执恒为 `UNATTRIBUTED`、无候选，不能完成任务。图片提交期间不提供候选；SDK 明确拒绝且未收到图片回执时保留此前归属能力。此边界不因回前台或迟回执自动解除，也不能重建实例绕过。进程重建仅恢复 OAuth，不能证明跨进程旧分享回执的归属；重复 URL/Universal Link 仍按 SHA-256 摘要去重。
- `cancel` 只结束库的本地等待，无法关闭微信页面。无 state 的老 SDK 授权回调被忽略，宿主可以在超时/页面离开时取消。宿主为每次调用生成不可复用的 requestId（最长 128 字符），库在实例生命周期内保留已使用 ID。
- 图片准备期间也占用请求槽位。Android Bitmap、iOS ImageIO 图像为内存数据；OHOS 图片文件在已交 SDK 后保留至精确匹配的图片回执，发送失败或未发送取消可立即删除；受理后不占请求槽，也不写可信 journal。缺回执或进程被终止后，原文件保留在 cache 等待系统清理，不以定时器猜测微信已读完；文件、ImageSource、PixelMap、ImagePacker 分别释放。页面销毁需调用 Kuikly `dispose()`；原生监听需对应移除并取消自己的请求。
- 回执可能早于异步 send completion 到达；宿主不应以“尚未收到 REQUESTED”为理由丢弃已严格校验的授权回执。

没有业务登录换票、roomId、分享任务完成、订单查询、业务文案和隐私授权流程。未实现普通 `PayReq` APP 支付。

## 可信冷启动恢复与迟挂监听

Android 构造参数 `store: WechatRequestStore?`、OHOS `configure(appId, context, store)` 和 iOS `store: WechatAuthorizationStore?` 均可选。没有 store 只支持当前进程请求。store 是宿主在隐私授权后提供的同步、原子持久存储，同一 App 只允许一个进程级客户端读写；读取错误不可降级为从回跳猜测请求。

- Android/KMP 记录 `WechatPendingRequest(requestId, transaction, kind, state)`；OHOS 同名结构的 `kind` 为 `authorization / share / merchant_transfer`，非 OAuth 的 `state` 为 `''`。transaction/state 由组件生成，发送 SDK **之前**写入；不能从 Intent、Want、回跳 URL 或 Kuikly 页面传入恢复快照。
- 消费、发送失败、取消先同步 `save(null)`，再结束等待或交付归一结果。宿主必须真正删除持久记录、禁止旧备份重放，并按账号/AppID 隔离、保护 OAuth state；不要记录其中的敏感字段。写入失败不会发送；清除失败不会交付，并需宿主修复存储后取消等待（Android/OHOS 可重新交 SDK 校验回跳）。
- 进程重建时先从 store 恢复等待，再将原始回跳交 `handleIntent` / `handleWant` / iOS 官方入口。只有 SDK 校验产生的响应，transaction、类型及 OAuth state 全部精确匹配时才消费；未知、类型错误、缺失/错误 state 和重复响应均拒绝。恢复本身不会发出 `REQUESTED`、不会再次发送请求；等待期间新请求仍 `BUSY`。
- Android `attach(listener)` / `detach()`，Swift `attach { receipt in }` / `detach()`，OHOS `addListener` / `removeListener` 支持迟挂监听。已归一回执只在本进程缓存（最多 64 笔），取出后不重放；取消同一 requestId 也会删除尚未交付的缓存。再次进程退出会丢失此缓存：本版本不承诺跨进程业务结果可靠投递，宿主用业务服务端核验兜底。
- OHOS Kuikly `attach(listener, restoredRequestId)` 只认领客户端已有的可信等待或归一缓存，不能导入 transaction/state。其他页面监听不会拿走此回执。页面 `dispose()` / native `onDestroy()` 取消其拥有的请求并释放监听；销毁后的页面不能复活请求。
- iOS 仅持久恢复 OAuth 的 `WechatPendingAuthorization(requestID, state)`。分享/转账继续返回 `requestID == nil`。分享只保留本进程单笔候选，按候选 ID 取消并清除本进程缓存；SDK 发送后取消触发上述隔离。不持久恢复分享，不用恢复记录伪造关联，不能据此标记资金到账。

例如 OHOS 宿主的 `trustedStore` 实现 `load(): WechatPendingRequest | null` 与 `save(request: WechatPendingRequest | null): void`；同步持久化和错误处理由现有宿主存储能力完成。先 `forwardWant`、后 `configure(..., trustedStore)`、再 Kuikly `attach(listener, restoredRequestId)` 即覆盖冷启动迟监听链路。

## Android 与 KMP 接入

远程 Maven 坐标（JitPack）：

```kotlin
implementation("com.github.gycrosskit.wechat:wechat-core:1.0.0")
// OHOS Kuikly 消费者额外添加：
implementation("com.github.gycrosskit.wechat:wechat-kuikly:1.0.0")
```

宿主在隐私授权后构造并持有唯一 `AndroidWechatClient(application, appId, listener, trustedStore)`；Android 构造及 Unit 入口可在任意线程调用，SDK 注册、store.load/save、状态与回调由组件串行到 Main。主线程即时执行，后台排队，Unit 返回不代表受理，必须等真实 `onSubmitted(REQUESTED)`。授权调用 `authorize(requestId)`；网页分享调用 `shareWebPage(requestId, url, title, description, thumbnailBytes, WechatScene.SESSION)`；转账参数全部来自服务端并原样传入 `openMerchantTransfer`。

```kotlin
client.shareImage(uniqueRequestId, imageBytes, WechatScene.SESSION,
    recipientId = trustedRecipientOpenId, senderOpenId = currentAccountOpenId)
```

两种 openId 由宿主可信账号链路提供，不记录、不写入 pending；pending 仍只存 requestId/transaction/kind/state。

**宿主必须自行实现 `{applicationId}.wxapi.WXEntryActivity`**。Activity 的 Main `onCreate` 与 `onNewIntent` 将 Intent 交给同一实例的 `handleIntent(intent): Boolean`（兼容旧行为，false 表示未处理，包含 SDK 异常）；后台调用使用 `handleIntent(intent) { handled -> ... }`，回调在 Main 返回 `Result<Boolean>`，成功值为真实 SDK Boolean，失败为异常，不阻塞等待，随后 `finish()`；不要直接读取 Intent 中的授权或转账字段，也不要创建第二个 SDK 实例。回跳期间 Application 冷启动仍要先接线；传入可信 `WechatRequestStore` 时首次 Main 状态操作恢复；没有恢复记录的旧回执仍被丢弃。

宿主 Manifest：

```xml
<activity android:name=".wxapi.WXEntryActivity"
    android:exported="true"
    android:launchMode="singleTask"
    android:theme="@android:style/Theme.Translucent.NoTitleBar" />
```

宿主配置 INTERNET 权限及微信开放平台的包名和签名。库 Manifest 仅合并 `queries/com.tencent.mm` 包可见性，固定 Activity 名称与签名不由库猜测。SDK 的 Intent 验签仍由官方 `handleIntent` 完成。

## iOS 原生与 KMP 接入

原生包可用远程 Git Pod：`pod 'GycWechatNative', :git => 'https://github.com/gycrosskit/wechat.git', :tag => 'native-1.0.0'`，它通过外部 CocoaPods 依赖精确版本 2.0.7，未上传 CocoaPods Specs。也可在 Xcode 添加仓库 URL 并按 revision/tag选择 `native-1.0.0`，使用 Swift Package 产品 `GycWechatNative`；Swift Package 不提供厂商 binaryTarget，宿主必须将官方 XCFramework 的目标平台 slice 加入 Swift/Framework 搜索路径并链接（CocoaPods 可自动管理）。单独添加此 Swift Package、未接线 WechatOpenSDK 时无法编译。

```swift
import GycWechatNative
// 主线程、隐私授权后，在 App 级容器中持有唯一实例：
let wechat = WechatClient(appID: hostAppID, universalLink: hostUniversalLink,
    onSubmitted: { requestID, status in /* 请求受理 */ },
    onReceipt: { receipt in /* Code 或 SDK 页面回执 */ })
```

`status` 为 `requested / busy / not_installed / unsupported / invalid_content / failed / cancelled`。UIApplicationDelegate/SwiftUI 把 URL Scheme 和 Universal Link 分别交给 `handleOpenURL` 和 `handleUniversalLink`。Info.plist 的 AppID URL Scheme、`LSApplicationQueriesSchemes`（`weixin`、`weixinULAPI`）、Associated Domains、Universal Link 域名服务端 AASA 与开放平台配置均由宿主负责。将授权 Code 返回宿主后不等待 UIApplication 激活，不额外保存凭据。

native-0.1.5 支持 `shareImage(requestID:data:scene:recipientID:senderOpenID:)` 的指定联系人路径。场景必须 `.session`，`recipientID` 非空且 `senderOpenID` 属于当前 AppID 的已认证发送账号；SDK 请求使用 `WXSceneSpecifiedSession`、`toUserOpenId` 和 `openID`。不从参数猜测当前账号，不退化到普通好友。普通分享省略 `recipientID`，保持原行为。已发布 `native-0.1.4` 仍含旧限制；[验证与发布边界](指定联系人分享对齐.md) 分别说明。

KMP 宿主实现导出的 `IosWechatBridge`，委托给原生 `WechatClient`，再创建 `IosWechatClient(bridge)`。完整适配示例为 [KmpWechatBridge.swift](../iosApp/KmpWechatBridge.swift)（构造时可传原生 `WechatAuthorizationStore`），当前示例用 framework 名 `WechatCore`；实际宿主改为其导出的 framework 名。示例已对真实生成的 KMP framework typecheck。

## HarmonyOS 与 Kuikly

历史候选 HAR `@gycrosskit/wechat-native@0.1.8-rc.1` 提供 `WechatPreferencesRequestStore`，宿主显式传入；默认 namespace 保持旧 `wechat_pending_${appId}`。旧 `0.1.1` 已上架。当前 HAR RC 位于独立 `har-0.1.8-rc.1` Release；OHPM Registry 安装、固定 Release HAR 消费与业务接线分别验收，实际渠道状态见发布记录。

```typescript
import { WechatClient } from '@gycrosskit/wechat-native';
// 隐私授权后，EntryAbility 先注册，再交回跳 Want 给官方 SDK：
const client = WechatClient.configure(hostAppId, context, trustedStore);
client.handleWant(want);
client.addListener(onReceipt);
const status = await client.authorize(uniqueRequestId);
// 页面结束：client.cancel(uniqueRequestId); client.removeListener(onReceipt);
```

EntryAbility `onCreate`、`onNewWant` 共用此入口。配置尚未完成时调用 `WechatClient.forwardWant(want)`，最多暂存 4 个 Want；配置完成后仍逐个交官方 SDK 验证。Bundle Name、identifier、签名指纹、官方回跳 schemes/skills 和微信开放平台审核均由宿主接线；库不解析 Want 的授权字段、不配置虚构的签名。未注册时不可使用 Kuikly Module；注册发生在宿主层，不从页面 JSON 信任 AppID。

Kotlin Pager 注册 `WechatModule.NAME to WechatModule()`，调用 `attach(listener)`；冷启动页面用 `attach(listener, restoredRequestId)` 认领宿主记录中的请求；ArkTS render 注册 `WechatModule.MODULE_NAME` 对应 `WechatModule`。两端 Module 名都是 `GycWechat`。页面销毁调用 Kotlin `dispose()`，取消本页面拥有的请求并释放 persistent callback。原生全局 SDK 不随 Kuikly 页面销毁。

## OHOS 工具链配置

本发布物使用 Kotlin `2.2.21-1.0.0`。普通 Kotlin 插件不提供 `ohosArm64()`，OHOS 消费者需匹配该工具链与 Native SDK。在 `settings.gradle.kts` 的 `pluginManagement.repositories` 中添加 `https://maven.eazytec-cloud.com/nexus/repository/maven-public/`，并保留 `google()`、`mavenCentral()` 与 `gradlePluginPortal()`；依赖仓库按 README 配置。插件版本和 Native SDK 由宿主统一管理，不再对各库单独配置一套。


### Android 线程与监听归属（Maven 0.1.5，0.1.4 尚不包含）

图片/thumbnail 在入口入队前复制，解码与压缩仍在 imageExecutor，SDK 发送回到 Main；Main `cancel` 可以取消尚未执行的入队请求，该请求不会打开微信且 requestId 不可复用。SDK 受理与最终回执仍分开，`REQUESTED` 不表示授权/分享/转账成功。

`attach/detach` 可在任意线程调用；已排队请求保留发起时的 listener 身份。detach 后迟回执缓存给原 listener，同一个 listener 重新 attach 可回放，新 listener 不接旧页面结果；请求没有 listener 或从可信 store 恢复的回执支持晚监听。缓存上限仍是当前进程 64 笔。

Android `cancel` 返回不保证清除完成；清除 store 失败不再从后台抛到调用线程，也不对原提交伪造 `FAILED/CANCELLED` 终态，pending 与 owner 保留，允许迟回执匹配和取消重试。未知 ID 不通知终态。同步 `handleIntent` 仅限 Main，兼容旧 false 表示未处理（含 SDK 异常）；后台必须选 callback 重载；异常通过 `Result.failure` 返回，不能以默认 false 当作 SDK 处理结果。

## Android/iOS Kuikly Native receiver

本版 Maven `0.1.9` 与 Git Pod `native-0.1.9` / 内部 `0.1.9` 提供本节 Native receiver。receiver 自 Maven `0.1.8` 引入，旧 Maven `0.1.7` 不包含此能力；本版发布与远程消费分别见顶部记录。`*-kuikly` 已声明 Android release、iosArm64、iosX64、iosSimulatorArm64 和 OHOS 变体，commonMain 使用同一个 Kotlin Module。iOS Native receiver 是可选 Git Pod `GycWechatNative/Kuikly`，其真实依赖为 `OpenKuiklyIOSRender 2.28.0`；默认 Native subspec 保留原生独立消费。

```kotlin
// commonMain；使用对应 Release 的精确版本。
implementation("com.github.gycrosskit.wechat:wechat-kuikly:1.0.0")
```

Android 在当前 Renderer 的 `registerExternalModule` 中调用组件扩展，参数是 Application 持有并处理 `WXEntryActivity` 回跳的同一个 client：

```kotlin
import io.github.gycrosskit.wechat.kuikly.registerWechatModule

registerWechatModule(applicationWechatClient)
```

iOS 使用 `pod 'GycWechatNative/Kuikly', :git => 'https://github.com/gycrosskit/wechat.git', :tag => 'native-1.0.0'` 固定远程版本。Main 配置同一个进程 client，并显式引用注册类型：

```swift
import GycWechatNative

WechatModule.clientProvider = { applicationWechatClient }
WechatModule.register()
```

Swift receiver 的 Objective-C 名精确为 `GycWechat`，由 SDK 为每个 Renderer 创建；Android 名由扩展绑定。`WechatModule.attach` / listen 不替换进程client的原宿主监听。receiver只观察自己的requestId，重复占用ID返回busy；restoredRequestId只匹配core可信pending/缓冲，不能抢走其他Renderer的ID。原始Intent、URL和UniversalLink仍由宿主交给同一个进程client，不在receiver解析或新增callback Activity。

原生入口在Main，onSubmitted只依据真实SDK发送结果，onReceipt独立投递；回执先于异步发送确认时两个事件都保留。iOS分享保持requestId=nil、candidateRequestId与SINGLE_PENDING，候选只用于送回原页面，不能升级为VERIFIED；iOS转账无可验证request/candidate，UNATTRIBUTED回执只交原宿主监听，不猜一个Renderer。

取消清除失败时保留原pending/owner；Android返回failed ack，iOS原生bool仅能返回no_pending（也包括存储清除失败），两者都不伪造原请求FAILED/CANCELLED。释放只移除本页监听并取消本页ID，绝不close或重建进程client，不绕过iOS分享quarantine。普通Swift Package继续导出Native能力；Kuikly receiver通过可选Git Pod消费。

Native Pod 使用静态 framework，以满足厂商 XCFramework 内静态库的链接条件。SDK receipt 与 submit ack 是两个不同入口；组件不新增公共 `source` 字段，宿主按这两个回调入口保持自己的业务来源映射与 UIApplication active / 当前 listener 准入。

同名 `GycWechatNative` 的 SPM 与 Pod 二选一。`GycWechatNative/Kuikly` 已包含 Native；使用该 subspec 后，不要再把 `native-0.1.6` 等 SPM Native 产品打包进同一进程。

销毁立即停止本页回调；原请求 ID 的 reservation 保留到 Main 完成取消并移除监听，之后才允许其他 Renderer 按可信 pending 恢复，避免旧清理取消新归属。

module.attach(listener)
